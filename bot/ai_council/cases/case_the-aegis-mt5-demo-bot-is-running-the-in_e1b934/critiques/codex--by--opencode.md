The persistence filter as described smuggles lookahead risk: "accepting a signal only when the state remains valid on the next bar" must translate to a one-bar-delayed entry executed at t+1 prices with costs recomputed, yet the proposal never specifies this, so a naive implementation consumes future information to inflate expectancy. The success criteria are half-unmeasurable — "≥10% net expectancy improvement" carries no significance test or minimum trade count (indistinguishable from fold noise), and "without materially increasing drawdown" defines no numeric bound, inviting post-hoc judgment calls dressed as pre-registration. Validation gaps: no fold count/walk-forward seeding specified, no multiple-comparison discipline if the threshold or filter parameters get revisited, and no commitment that the sealed holdout is touched exactly once — iterative re-checking burns the seal. Finally, "candidate successful" must not imply promotion: any pass must still traverse every gate in `promote.py`, an omission the proposal quietly leaves open.
